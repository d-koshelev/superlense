# Review a plan

1. Read the proposal and the request it is meant to satisfy. Identify who needs what outcome, the starting conditions and any constraints that could change the decision. For a repair, locate the original failure and its evidence. For new work, use the observable result the user wants.
2. Trace each consequential step from the condition it changes to the effect the user would see. Cite the record that supports the link. Try completing the step exactly as written while the original problem persists. If that is plausible, say where the chain breaks. Distinguish an observed failure from a suspected cause. When competing explanations imply different fixes, name the smallest observation that would distinguish them and say which work can proceed meanwhile.
3. Compare the proposed change with a smaller feasible intervention or the working baseline under the same constraints. Group steps only when the same change resolves their failures. Keep necessary containment, including who or what it protects and when it can end. Keep independent safeguards with a distinct purpose. Check the order where a step depends on another or could disrupt something that already works.
4. Give the decision first. Identify what to keep, change or defer, the reason and the evidence for each material change. For a disputed step, specify what the user would observe after the correction in the original case and in a nearby case that already works. A completed checklist can coexist with a failed outcome. If the plan holds up, say why and leave it intact. Return findings in the assigned channel. When asked to revise the plan, put the changes in the requested destination. A review alone authorizes no execution of its steps.
